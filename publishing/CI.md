# Continuous integration

The repository has one Android Gradle module, `:app`. It uses AGP 9.1.1, Gradle 9.3.1, Java 11 source/target compatibility, JUnit 4 and Kotest JVM tests through JUnit Platform/Vintage. Android/Compose tests are under `app/src/androidTest`. The full test inventory and audit are in [TESTING.md](../TESTING.md).

## Checks

| Event | Checks |
| --- | --- |
| Pull request to `main` changing an app component | Debug APK build, strict `lintDebug` including test sources, `detekt`, all debug JVM tests and JaCoCo, mapped Android test classes and `SmokeTest` on an API 35 emulator; SonarQube Cloud analysis and Quality Gate |
| Push to `main` changing `gradle.properties` for a version/release | Full Windows Android CI for the exact release commit; release verification reuses its instrumentation/smoke evidence. Release JVM/lint and signed APK/AAB checks remain independent |
| Shared or unmapped build input | Debug build, lint, detekt, full JVM and Android regression, JaCoCo, smoke, and Sonar analysis |
| Documentation or AI instruction/script-only change | Path classification only; no Java/Gradle setup, Android build, tests, or Sonar analysis |
| GitHub API or release script-only change | Pester or PowerShell syntax respectively; no Android build or tests |
| CI script-only change | Selector/gate unit tests and full app regression |
| `v*` tag or manual release verification | All JVM, Android, and CI/tool correctness tests, debug/release lint, detekt, JaCoCo, Sonar, launcher smoke, signed APK/AAB builds, signature and archive checks |

Available test and lint reports are attached to CI runs; detekt HTML/SARIF and coverage are attached for every app change. Signed release artifacts are attached to release verification runs. Tag/manual runs verify a candidate with their own full Ubuntu/API 35 instrumentation and Sonar analysis, without publishing. A main-branch change to `gradle.properties` publishes only after release JVM/lint regression, verified full Windows instrumentation/smoke evidence (including the CI Sonar Quality Gate), and signed artifact checks pass. Windows is the deliberately chosen single full Android regression environment for main publication; Windows/Ubuntu equivalence has not been experimentally established. This does not replace a manual device/store review.

`tools/ci/select_checks.py` classifies changes from the event base commit. Repository Markdown outside `app/`, `AGENTS.md`, `.agents/`, and `.codex/` need no app tests or Sonar analysis. GitHub API and release scripts have their own focused checks; CI scripts also run full app regression because they control test execution. Changes to multiple app areas union their mapped test classes. `GameSession`, `GameViewModel`, `MainActivity`, Gradle, manifest, workflow, and any unknown path run full regression; unresolved diffs do too. The selector's output determines the CI steps. For app changes, debug JVM coverage always uses the complete debug suite (never filtered coverage); mapped Android selection is retained. An explicit final assertion rejects invalid selector outputs and missing, skipped, failed, or masked required steps, and an Android XML report check rejects an empty or incorrectly filtered run. `EnergyScenarioTest` remains an opt-in measurement. The stable `android` job reports a result for every PR, including documentation-only changes. A newer push to the same PR cancels its older in-progress Android CI run; pushes to `main` are not cancelled.

New production Kotlin files must be registered in `SOURCE_GROUPS` or `FULL_SOURCES`; the release selector tests reject unclassified files. Register the layout and pixel tests for a new renderer alongside its mapping.

The Windows device script runs launcher smoke (`adb shell monkey` with one launcher event) immediately after installing the app/test APKs, before instrumentation. A failed launcher stops the device step; stale device reports are removed first. Full-regression evidence is written only after instrumentation and its report validation also succeed. This launcher check is separate from the `SmokeTest` instrumentation class, which exercises new game, pause and Continue. A launcher event alone does not verify changed gameplay, rendering, persistence or platform behavior.

Use the existing selector instead of running full Android regression for every PR. For example, a JVM-test-only change selects `SmokeTest` as the only Android class while retaining JVM/quality/Sonar checks; repository documentation selects no Android tests. A launcher event alone is not an exemption for production code. The table and selector above remain the source of truth for affected checks.

### Short feedback loop without reducing verification

1. Inspect the diff and affected behavior before choosing local checks. Prefer focused JVM tests for framework-independent rules and calculations; use instrumentation for Android integration, persistence/lifecycle, UI, gestures and rendering that JVM tests cannot demonstrate. Do not migrate or delete existing tests merely to fit a test pyramid, and do not add more device coverage without an identified risk.
2. Run the smallest relevant local checks at meaningful checkpoints in one issue. After a failure, preserve diagnostics, distinguish an application bug from a broken/outdated test, fix the cause and run the failed scenario first. Check nearby behavior affected by the fix before the final required CI. Do not use automatic retries to turn a failure green or repeat unchanged successful suites after every small edit.
3. Prepare the issue's final diff before pushing for its mandatory PR check. The current commit must pass the existing selector's required checks; updating from newer main requires verification of that new state. Do not defer verification of unmerged gameplay to the end of an epic. Existing per-PR concurrency cancels superseded attempts of that PR, not other PRs or release work.
4. Reuse compatible Gradle task outputs with incremental builds/build cache. Avoid `clean` unless stale outputs or a reproducibility check justify it. Distinguish executed tests from cached/up-to-date tasks in reports; cached outputs are not a claim of fresh test execution. Keep test isolation, the wiped headless CI emulator and release evidence binding.
5. Wait for observable UI/lifecycle/platform conditions with bounded synchronization, rather than adding unconditional sleeps or broadly increasing timeouts. Use the API available in the pinned Compose version; new documentation does not justify upgrading dependencies for this task. Keep real elapsed-time assertions where elapsed time is the behavior being tested.
6. Measure runner queue time and actual build/analysis/emulator/test time separately. Compare successful runs with the same scope and environment before claiming a speedup. An early launcher failure can avoid the remaining instrumentation work; a successful run still executes all checks selected for its changes.

These choices adapt the official [Android testing strategy](https://developer.android.com/training/testing/fundamentals/strategies), [what to test](https://developer.android.com/training/testing/fundamentals/what-to-test), [Compose synchronization](https://developer.android.com/develop/ui/compose/testing/synchronization), [Gradle performance guidance](https://docs.gradle.org/current/userguide/performance.html) and [GitHub concurrency guidance](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), reviewed on 2026-10-09. Their example device matrices and post-merge schedules are not additional Swypetris requirements. Full release gates and existing quality thresholds remain unchanged.

The required merge check is `android` from GitHub Actions (app ID 15368). App changes run build, lint, detekt, complete debug JVM tests, JaCoCo, and report validation before Sonar analysis. The scanner uses `sonar.qualitygate.wait=true`, so a failed Quality Gate, missing configuration, untrusted fork, or scanner timeout fails the required job before it starts the emulator. Android instrumentation and smoke then run for a passing analysis. A failed earlier gate skips the device step, while report upload and the final required-step assertion still run and keep `android` failed. Documentation-only changes skip those steps and do not wait for a separate SonarCloud check. Merges that do not change `gradle.properties` do not repeat the suite on a `main` push; the PR check already tested against current `main` under strict protection. Tag/manual release analysis uses the release ref name and waits for its Quality Gate result. Main publication reuses the same-commit CI Quality Gate together with the full instrumentation evidence below, avoiding a second Sonar scan.

### Full regression evidence and main release gate

After a successful full Windows run, `tools/ci/full_regression_proof.py` creates `full-regression-<run_id>-<run_attempt>`. It contains the tested debug APK/test APK, raw instrumentation and launcher smoke reports, environment details, tracked app/build/CI configuration blob IDs, and a manifest with individual SHA-256 hashes and workflow identity. Full mode must be unfiltered. The report must terminate successfully, account for every declared Kotlin instrumentation test exactly once (including existing opt-in skips), and actually pass `SmokeTest`. Unsupported inventory declarations fail closed. Selected/none runs do not produce this evidence.

`tools/ci/wait_for_android_ci.py` waits up to 30 minutes for the latest main-push run of this repository's active `ci.yml` at the exact release SHA. It verifies the current attempt's successful Windows `android` job and required steps, including lint/detekt/JVM/reports/Sonar/device/evidence upload/final assertion. It downloads only that run/attempt's named artifact and checks the API archive digest, file hashes, APK archives, run/workflow/repository/SHA/ref/attempt binding, complete reports, source inventory, configuration and recorded Windows/API 35 x86_64 environment. Expired, missing, corrupt, selected/none, failed, skipped or cancelled evidence cannot authorize publication. An older success cannot hide a newer pending or failed attempt. The latest run/attempt is checked again after validation.

For main pushes, the always-present release `instrumented-tests` job is an explicit successful evidence gate; it does not boot an Ubuntu emulator or build debug test APKs. It saves `verified-main-regression.json` identifying the accepted run, attempt, SHA and artifact digest. Tag/manual use that job for their independent full Ubuntu regression. `publish` requires successful `regression`, `instrumented-tests` and `signed-release`, rejects skipped/failed/cancelled dependencies, and revalidates the latest full CI attempt immediately before publication. Only the evidence gate and publisher receive Actions read permission. Signed release builds/lint, certificate fingerprints, APK version metadata, AAB archive verification and published hashes are unchanged. Verification proves the selected state when checked; a future rerun does not retroactively change an already published release.

Local policy verification uses `python -m unittest discover -s tools/ci -p 'test_*.py'`, PowerShell parsing for the device script, and actionlint for both workflows. Routing tests exercise main/tag/manual conditions and unsuccessful dependencies; they complement GitHub execution rather than emulate the whole service. End-to-end main reuse/signing/publication requires a real authorized version-change event and is not implied by a passing PR run. No measured speedup is claimed.

The `android` job runs on a local Windows x64 runner labelled `swypetris-android`. GitHub dispatches the job and records its required result; Gradle, lint, detekt, JVM tests, JaCoCo, emulator tests, and the Sonar scanner execute on that computer. The Sonar Quality Gate is still decided by SonarQube Cloud. The debug APK, lint, and Android test APK build commands use Gradle's local build cache for reusable task outputs; JVM and instrumentation tests still execute for every selected run. Cache hits and elapsed-time savings depend on the inputs and runner state and must be measured rather than assumed. Prepare Java 21, Python 3 available as `python3`, PowerShell 7, the Android SDK/API 35 system image, and a dedicated `SwypetrisCI35` AVD before registering the runner. The device step boots that AVD headlessly on `emulator-5556`, installs both APKs with that explicit serial, and runs `am instrument` against it. The raw instrumentation report is checked for completed tests and the requested classes; the connected phone and any existing emulator are never selected. Register an ephemeral runner for the intended trusted PR or main commit and let it unregister after one job. In this public repository, never leave a runner with access to the normal user profile online for unreviewed external PR code. The job has a 35-minute timeout; investigate stalls and preserve logs before retrying. Release signing remains in the separate release workflow.

Main protection now has `required_status_checks.strict=true`, enabled by an explicitly authorized PATCH to the status-check protection endpoint and verified by rereading the whole protection object. The `android` check retains app ID 15368; all other protection parameters are unchanged. Before merging, fetch current main. If it advanced after the PR's verified state, preserve local edits, merge main into only the owned PR branch, push the new commit, and wait for its required CI. A passing run from the previous commit is insufficient. Do not alter another active task's branch or worktree.

On Linux/macOS, run broad local checks with `bash ./gradlew :app:assembleDebug :app:lintDebug :app:testDebugUnitTest :app:jacocoDebugUnitTestReport`; CI uses the selector above for focused changes. Run all JVM variants with `bash ./gradlew :app:test`. Run instrumentation on a selected emulator with `ANDROID_SERIAL=<serial> bash ./gradlew :app:connectedDebugAndroidTest`. Use JDK 21 for the Sonar scanner. On Windows, `tools/Verify-Tests.ps1` runs and summarizes the fast checks or instrumentation on an explicitly selected emulator; see [TESTING.md](../TESTING.md).

JaCoCo XML is produced for every app change at `app/build/reports/jacoco/jacocoDebugUnitTestReport/jacocoDebugUnitTestReport.xml`. Selective Android CI also runs the complete debug JVM suite, so Sonar never receives filtered whole-app coverage. A separate `Validate quality reports` step (`quality_reports`) verifies executed JVM tests, covered production lines in JaCoCo XML, no lint Error/Fatal results, and detekt report presence. It runs after the JVM step, including after earlier failures unless the workflow is cancelled. Report validation failure does not change the JVM step's successful outcome, but both are required by the final assertion for selected/full runs. It measures production Kotlin classes compiled for the debug variant, excluding generated `R`, `BuildConfig`, and `Manifest` classes. It includes only JVM-test execution; Android instrumentation/Compose UI coverage is not merged. Do not interpret its overall percentage as complete application coverage.

## SonarQube Cloud setup (Issue #63)

1. Import `RoyMatus/Swypetris` into SonarQube Cloud and choose CI-based analysis. Disable automatic analysis if the imported project enabled it, to avoid duplicate analyses. Record the exact organization key and project key shown there; do not infer either from the GitHub name. Confirm the SonarQube Cloud region and configure it if the project uses the US instance.
2. Add repository **Actions variables** `SONAR_ORGANIZATION` and `SONAR_PROJECT_KEY` with those exact values. If the project is in the US region, also add `SONAR_REGION=us`; the EU instance needs no region variable. Add repository **Actions secret** `SONAR_TOKEN` with a token that has analysis permission. On GitHub, open **Settings → Secrets and variables → Actions → Secrets → New repository secret**. Paste the token there, not in chat, a file, or a PR.
3. Run CI on `main` to establish a baseline, then inspect a PR analysis and confirm that the JaCoCo XML was imported. App changes fail if either variable or the token is missing. Pull requests from forks cannot run token-based analysis because GitHub does not pass repository secrets to forked PR workflows; move reviewed app changes to a trusted repository branch before merging. Documentation-only changes need no Sonar credentials.
4. The project uses the dedicated `Swypetris` Quality Gate: new-code reliability and maintainability ratings must be A, new-code duplication must be at most 3%, and new security issue severity must stay below High. Medium/Low security findings and hotspots require manual review. Coverage is reported without a gate threshold until the test audit in #62. Historical findings do not block the gate. Require the stable `android` GitHub Actions check on `main`; its scanner step waits for this Quality Gate for app changes. Do not also require the separate `SonarCloud Code Analysis` check, which is absent for documentation-only changes.

### Required check

The active main policy requires `android` from GitHub Actions (integration/app ID 15368) with strict up-to-date checking. See [POLICY.md](POLICY.md) for the enforcing mechanism and API maintenance. The separate SonarCloud check is not mandatory for documentation-only changes.

The scanner excludes Gradle `build` and generated directories plus PNG, OGG, and WAV assets. Kotlin and Java sources remain in scope. Its coverage input is the XML report above. If coverage is missing, check that `:app:jacocoDebugUnitTestReport` ran and that the XML exists in the CI artifact. If scanner authentication fails, check project keys, region, token permission, and the `SONAR_TOKEN` secret without printing the token. For a failed Quality Gate, inspect the SonarQube Cloud project/PR dashboard and the GitHub check.

## Release signing secrets

The local release process uses separate keys for the directly distributed APK and Google Play upload AAB. Configure these **repository Actions secrets** before using `release-check.yml`:

| APK application key | AAB upload key |
| --- | --- |
| `SWYPETRIS_APP_KEYSTORE_BASE64` | `SWYPETRIS_UPLOAD_KEYSTORE_BASE64` |
| `SWYPETRIS_APP_STORE_PASSWORD` | `SWYPETRIS_UPLOAD_STORE_PASSWORD` |
| `SWYPETRIS_APP_KEY_ALIAS` | `SWYPETRIS_UPLOAD_KEY_ALIAS` |

Base64 values must encode the corresponding `.p12` keystore files. The workflow restores them into the runner's temporary directory and does not commit them. Missing secrets deliberately fail the signed-release job. The verification step checks the APK and AAB signatures and compares each signer's SHA-256 certificate fingerprint with the matching public certificate in `publishing/certificates/`. `jarsigner -verify -strict` is deliberately not used: Android upload certificates are self-signed and strict chain validation rejects a valid app bundle.

## Cloud GitHub release

Changing `swypetrisVersion` on `main` triggers release verification. Increase the Android versionCode as part of the same release change. Only the final publish job receives contents-write permission; signing jobs keep read-only permissions. Signing keys remain in the runner temporary directory. APK metadata and SHA-256 are read from the verified signed APK, then `Swypetris.apk`, `update.json`, and `SHA256SUMS.txt` are published to a new version tag. An existing release is never overwritten. Tag/manual runs verify artifacts without publishing.

## detekt policy

The `dev.detekt` plugin is pinned to `2.0.0-alpha.3`, the first release whose compatibility table matches AGP 9.1.1 / Gradle 9.3.1 and supports AGP built-in Kotlin without the old-DSL workaround. This is a prerelease dependency, not a stable 2.0 release. Application dependencies and compiler versions are unchanged. The plain `:app:detekt` task scans all `src/**/*.kt` (main, JVM tests, Android tests) without type resolution. Type-resolution-only rules are not claimed to run. It uses default rules plus validated configuration and fails on Warning or Error. HTML and SARIF are retained as artifacts; no formatting plugin, autocorrection, or baseline is added. The framework naming convention is documented below.

Lint explicitly fails on Error/Fatal, includes test sources, and generates HTML/XML/SARIF. Warnings retain existing severity; no rule is disabled. CI continues collecting other check results after a detekt/lint failure, but the job remains failed and the final assertion rejects the unsuccessful steps. Existing-code violations must be fixed or individually reviewed in a separately approved policy; a green CI result is not promised by enabling these checks. See [CI-AUDIT.md](CI-AUDIT.md).

Screenshot test methods that use the API-26 capture API declare `SdkSuppress(minSdkVersion = 26)`; screenshot helpers declare `RequiresApi(26)`. Other methods retain their existing supported API range. API-35 CI executes these screenshot tests. Lint has no baseline. The delivery correction also uses `Typeface.NORMAL` and the public `ViewModelProvider` factory in tests instead of a literal font style and restricted `ViewModelStore.put`.

Compose naming policy: FunctionNaming ignores only @Composable declarations because the official Compose API guidelines prescribe PascalCase for Unit-returning UI components. Ordinary functions retain the default camelCase check. This is a targeted framework convention, not a legacy baseline; other rules and failure thresholds are unchanged. Reference: https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/docs/compose-api-guidelines.md
