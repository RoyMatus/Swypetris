## Working safely

- Inspect affected code first; make the smallest complete change. Preserve architecture, language, naming and dependencies; do not edit generated files or perform unrelated cleanup/upgrades.
- Use a separate worktree. Preserve pre-existing changes and other processes' branches, worktrees and workflow runs. Clean up only your merged, unused branches/worktrees after checking open PRs, unmerged work, local changes and needed artifacts.
- For a new, changed or uncertain affected API/framework contract, consult current documentation through the authenticated Context7 plugin when available and check its version/API scope. Reuse that research until the version or contract changes. If no configured connection works, consult official documentation; do not repeatedly retry exhausted quotas.
- Prefer repository API scripts and CLI over UI automation. Never print or commit credentials, signing keys or other secrets; do not expand access without authorization.
- Before starting an epic, resuming it on another machine, or implementing a standalone ticket, diagnose the actual execution host with `tools/Get-ExecutionProfile.ps1 -Context '<epic/ticket>'` and follow [publishing/EXECUTION-PROFILES.md](publishing/EXECUTION-PROFILES.md). Run all builds, tests, tool checks and release verification locally. On a constrained host reduce concurrency or wait for a suitable local executor; missing local capacity blocks verification and never authorizes cloud execution. SonarQube Cloud is the sole analysis-service exception: its scanner runs locally and waits for the remote Quality Gate. A phone is a client, not evidence of backend capacity. Record the profile/reason; recheck after resource/toolchain changes, not before every command. Keep required local final-PR and exact-main signed release gates.
- Delegate only distinct work whose expected benefit exceeds coordination cost; assign file ownership and share the host profile, resource budget and completed checks. One owner schedules heavy builds/device tests; agents must not duplicate discovery or rerun unchanged successful checks. Use the relevant project role/skill; simple delegated work uses `gpt-6-luna` with low effort. The parent owns integration and final verification.

## Store compliance gate

- Before implementing any user request or ticket, check [RuStore compliance memory](publishing/RUSTORE-COMPLIANCE.md) and the applicable current mandatory rules. Do not implement a confirmed conflicting part, even if it appears in the request or ticket; explain the exact provision/evidence and offer a compliant alternative while continuing independent compliant work. Investigate uncertainty without presenting it as a violation; recommendations are not mandatory rules.
- Use the `store_compliance` role in `.codex/agents/store-compliance.toml` for substantial or uncertain compliance scope and before publication. If the role is not loaded in this session, assign its exact read-only instructions to an available agent; do not claim the custom role is active. Reuse verification evidence and preserve the separate technical and compliance release gates.
## Scope, design and gameplay

- Existing layout/design is protected. Change only requested visual elements; preserve adjacent placement, proportions, spacing, colors, typography, icons, textures and animations. Material product/design decisions outside authorization belong to the user.
- The game always uses portrait orientation. Preserve the portrait Activity lock; do not enable or force landscape orientation in application code or tests. Verify UI on relevant portrait screen sizes, aspect ratios and font scales.
- Derive UI geometry from available space/insets; use dp/sp bounds and accessibility minimums; avoid device-specific pixels.
- Keep gameplay logic and tunable rules in their existing single owners. Preserve state across navigation, backgrounding and configuration changes; avoid duplicate sources of truth.
- Check affected interactions among scoring, spawning, collision, merging, progression, victory and loss. Preserve unrelated mechanics. Difficulty remains Easy / Medium / Hard with centralized parameters and balanced early pacing.
- Pause returns to the main menu with Continue; do not add a pause screen. Game indicators stay near the upper-left with a small consistent inset-aware margin.

## Delivery

- Prepare and verify code and complete GitHub-facing text locally before writes; use English. Use `tools/Update-Issue.ps1` and `tools/Manage-PullRequest.ps1`, preview supported writes with `-WhatIf`, and verify API results.
- Before the final PR push, finish the code, selected development checks, diff review, PR text, release notes and measurements that belong in that PR. A draft PR may be created after this preparation to obtain the PR number needed by local Sonar analysis; finish the final local gate before marking it ready or merging. Record the risk each check addresses; rerun successful unchanged scope only for a meaningful change or new evidence. During local final verification, prepare the completion report without changing the tested commit. Keep compatible caches in the owned worktree through sequential tickets; never force clean/rerun by habit.
- Use one risk-based check plan per ticket and reuse its completed evidence across agents. Local checkpoints are not an instruction to repeat unchanged successful checks before the final local PR gate. Documentation-only work needs review; local tool changes need tool tests. Full regression belongs to cross-system changes, unresolved failures and release gates. Do not dispatch GitHub Actions, install a self-hosted Actions runner or schedule cloud checks; batch changes before the final local gate. Consult affected API documentation once per task/API uncertainty and reuse it until a relevant version or contract changes.
- Implement epic issues sequentially: one linked branch/PR per issue, merge and confirm closure before the next. State the concrete issue plan in chat. Project Priority, Work Type and Testing need evidence-based agent judgment; keep Status aligned with actual progress. After ProjectAccessError, report once and stop Project operations until credentials change.
- Prepare issue/epic metadata and concise completion comments through [publishing/DEVELOPMENT-WORKFLOW.md](publishing/DEVELOPMENT-WORKFLOW.md). Detailed time journals are optional; report unrecorded time as unknown. Keep unstarted prepared work in Backlog; preserve explicit On Hold until resumed.
- Put `Closes #N` in the PR body for merge-driven issue closure. Confirm closure after merge and add one consolidated issue comment containing completed behavior, actual checks and PR URL; do not redundantly close an already closed issue.
- GitHub enforces PRs and main/tag integrity protections; the local merge script enforces verification. Use Manage-PullRequest.ps1 with valid local evidence for the exact PR head and current main base. UI/API merges outside that script bypass the local test gate and are not the approved delivery path. Keep the tested tree clean and preserve local work when updating it. Never bypass failed or missing checks. If a local check stalls, preserve diagnostics and diagnose before retrying; stop only processes owned by this task. See POLICY.md for enforcement ownership.

## Verification and reporting

- Use TDD by default for new or changed testable logic and reproducible bug fixes: derive a behavior test from acceptance criteria, observe its expected failure before implementing the behavior, make it pass, then refactor with the affected tests green. Follow [TESTING.md](TESTING.md#tdd-for-behavior-changes) for scope, exceptions and RED/GREEN evidence; record any exception and alternative checks in the ticket's check plan. Environment/build failures do not prove behavior RED, and intermediate RED evidence never replaces a passing final gate.
- During each epic, retain selected local check evidence, actual durations/counts, failures/retries and relevant rework. After the epic's implementation merges, create one concise English review in `publishing/reports/epic-<number>-development-review.md` and link it from the epic. Separate measured facts from inferences and unknowns; propose an optimization only when evidence supports it and state quality-preserving validation. Do not invent timings or claim causality from cold-versus-warm comparisons.
- `tools/release/Record-EpicWork.ps1` is optional for observed phase boundaries; `tools/release/New-TicketCompletion.ps1` and `tools/release/New-EpicReview.ps1` prepare local drafts from selected evidence. Stop an active journal interval when leaving or waiting; missing intervals stay unknown. Preserve emulator diagnostics before retrying and profile measured slow tests before changing synchronization. After publication, use `tools/release/Verify-PublishedRelease.ps1`; its artifact checks do not replace instrumentation, physical-device acceptance or the release gate.
- Review the diff and choose the smallest checks covering changed behavior using `android-test-selection`; CI selection is not a substitute for local risk assessment. Do not build Android for instruction-only edits. Fix regressions introduced by the task; preserve full failure logs in ignored build output.
- Before device tests, inspect `adb devices -l` and identify serial/model. Use an isolated headless emulator (`-no-window`) first and always select an explicit serial. Open a window only when required for visual/manual verification.
- Use the connected Pixel 7 when real-device behavior, update compatibility or release acceptance needs it; explain the risk covered. A documentation or local-tool-only merge does not require reinstalling the game. Authorized Swypetris uninstall may remove its data; never uninstall unrelated apps. Leave Swypetris installed afterward.
- Separate facts, inferences and uncertainty. Never claim a build, test, scanner, setting change or merge without its result; install success is not a passed instrumentation test. Report changed behavior/files, actual checks, relevant logs and remaining limitations concisely.
